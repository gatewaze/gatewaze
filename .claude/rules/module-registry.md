# Module registry (`packages/portal/lib/modules/generated-*`)

The portal has a generated module registry that maps URL paths to
lazy-loaded module pages. This file is **gitignored** and regenerated
by `packages/portal/scripts/generate-module-registry.ts`.

## What gets generated

| File | Generated by | Consumed by |
|------|-------------|-------------|
| `lib/modules/generated-portal-modules.ts` | `walkPortalPagesDir` | `app/(main)/m/[...path]/page.tsx` (catch-all router) |
| `lib/modules/generated-event-pages.ts` | `discoverEventPages` | event-detail layout (event-pages slot) |
| `lib/modules/generated-portal-rewrites.json` | derived from prefixes | `next.config.ts` rewrites |
| `lib/modules/generated-modules-dirs.json` | resolved source paths | `next.config.ts` webpack alias |
| `lib/modules/generated-module-prefixes.json` | unique moduleIds | middleware URL routing |

## How the generator emits import paths

The generator currently emits **absolute filesystem paths** as the
dynamic-import target:

```ts
component: () => import('/premium-gatewaze-modules/modules/calendars/portal/pages/[slug]/about')
```

That's the path as resolved at generation time. In Docker, the entry
point symlinks `/premium-gatewaze-modules` to the actual repo so the
import resolves at runtime. Locally, the path is
`/Users/dan/Git/gatewaze/premium-gatewaze-modules/...` if generated on
your machine.

### Why this triggers TS errors locally

When the generated file contains paths like `/premium-gatewaze-modules/...`
that don't exist on your local filesystem, TypeScript reports
TS2307 ("Cannot find module") for each import — about 27 errors total
across the two generated files. These are environment-specific noise,
not a real regression.

If you regenerate locally with the local sibling repos present, the
paths become `/Users/dan/Git/gatewaze/premium-gatewaze-modules/...` and
TS resolves them — but then it transitively typechecks the external
module sources, which surface ~200 their-own errors.

### What we tried and abandoned

In the prod-hardening pass we tried two refactors of the import paths
and reverted both:

1. **Alias paths via `@gatewaze-modules/*`**: emits resolve correctly
   in both Docker and local, but TS recursively typechecks the external
   modules, ballooning local error count to 248. Reverted.

2. **Ambient module declarations** (`declare module '/premium-gatewaze-modules/*'`):
   doesn't work because TypeScript treats paths starting with `/` as
   relative/absolute and skips ambient declarations for them.

Both attempts are documented in commit `a16de23` and the surrounding
session work; don't re-attempt unless you have a new approach (e.g.
generated Database types or a different alias-resolution strategy).

### CI works correctly

CI rebuilds the registry fresh in the build environment with the
right module-source paths, so the local-vs-CI discrepancy doesn't
affect deploys. The local TS error count for these two files is a
known artifact.

## When you add a new module page

Module authors don't write to these generated files directly — they
add `portal/pages/<route>.tsx` to their module repo, and the
generator picks it up automatically when run.

The generator is invoked by:
- `packages/portal/scripts/generate-module-registry.ts` — directly
  (via `npx tsx`)
- The portal's dev server start hook
- Docker build time

If you're adding to or changing the generator itself, run it and
inspect the output:

```bash
cd packages/portal
MODULE_SOURCES='/Users/dan/Git/gatewaze/premium-gatewaze-modules/modules#label=Premium' \
  npx tsx scripts/generate-module-registry.ts
```

## The `@gatewaze-modules/*` alias

`packages/portal/tsconfig.json` and `packages/portal/next.config.ts`
both define an alias `@gatewaze-modules/*` that resolves to the first
matching module dir on disk:

```ts
// next.config.ts
config.resolve.alias = {
  ...(config.resolve.alias || {}),
  '@gatewaze-modules': moduleAliasPaths,  // ← array of resolved dirs
};
```

Real (non-generated) consumers of the alias work fine:

```ts
// packages/portal/app/api/portal/listing/[module]/route.ts
import { eventsListingSchema } from '@gatewaze-modules/events/listing-schema';
```

These imports DO get typechecked. So `events/listing-schema.ts` in the
public gatewaze-modules repo IS subject to the portal's TS error count
and CI gates. Module authors in that repo should run `pnpm --filter
@gatewaze/portal typecheck` if they're touching shared schema /
contract code.

## The three module repos

| Repo | Sibling path | Modules |
|------|------|---------|
| `gatewaze-modules` (public) | `../../gatewaze-modules` | Open-source modules: events, etc. |
| `premium-gatewaze-modules` (private) | `../../premium-gatewaze-modules` | Premium modules: event-invites, kiosk, virtual-events, calendars, recipes, blog, newsletters, forms, etc. |
| `lf-gatewaze-modules` (Linux Foundation) | `../../lf-gatewaze-modules` | Brand-specific modules: podcasts, etc. |

Each repo has its own toolchain and CI. The portal doesn't typecheck
their internals — that's their responsibility.

## When you DO want to typecheck an external module

Run `pnpm typecheck` IN that module's repo, not in the portal. The
portal's typecheck is intentionally scoped to the portal's own source
tree.
